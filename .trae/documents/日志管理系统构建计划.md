# 日志管理系统构建计划

## 概述

构建一个完整的日志管理系统，包括后端日志系统重构 + 日志查询 API + 前端日志管理页面，支持按级别/时间/关键词/request_id 精准定位错误。

## 现状分析

### 后端日志问题
1. **所有 handler 挂在 root logger 无过滤** — `app.log`、`api.jsonl`、`audit.jsonl`、`perf.jsonl` 内容大量重复
2. **request_id 未传播到业务日志** — 中间件生成了 request_id 但仅写入 perf 日志，业务日志无法关联请求
3. **config.yaml 日志配置未被使用** — `settings.logging` 被加载但 `setup_logging()` 全部硬编码
4. **无结构化日志查询能力** — 日志仅写入文件，无法通过 API 查询

### 前端
- 无日志管理页面，导航菜单无日志入口

## 改动范围

### 后端（5 个文件修改 + 1 个新建）

#### 1. 重构 `backend/app/core/logging_config.py` — 日志系统核心重构

**目标**：按 logger 名称路由 handler，消除重复；从 config.yaml 读取配置；添加 request_id 注入。

- 用 `logging.Filter` + `contextvars` 实现 request_id 自动注入每条日志记录
- 按名称分配 handler：
  - root logger: 仅挂 `app_handler`（文本格式）+ `error_handler`（ERROR+）
  - `app.api` logger: 挂 `api_handler`（JSON 格式），`propagate=False`
  - `perf` logger: 挂 `perf_handler`（JSON 格式），`propagate=False`
- 从 `settings.logging` 读取文件名/级别/maxBytes/backupCount，不再硬编码
- 添加 stdout handler（开发模式，级别受 `settings.app.debug` 控制）
- `JsonFormatter` 增加 `request_id` 字段

#### 2. 修改 `backend/app/core/middleware.py` — request_id 传播

- 在请求开始时将 `request_id` 写入 `contextvars.ContextVar`
- 请求异常时也记录性能日志（try/finally 包裹 `call_next`）
- API 请求日志使用 `app.api` logger 而非 root logger

#### 3. 新建 `backend/app/api/logs.py` — 日志查询 API

**端点设计**：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/logs/files` | 获取日志文件列表（文件名、大小、最后修改时间） |
| GET | `/api/v1/logs` | 查询日志条目（支持分页、级别过滤、关键词搜索、request_id 过滤） |

**`GET /api/v1/logs` 参数**：
- `file` (str): 日志文件名，默认 `app.log`
- `level` (str): 日志级别过滤（ERROR/WARNING/INFO/DEBUG），默认不过滤
- `search` (str): 关键词搜索（在 message 中模糊匹配）
- `request_id` (str): 按 request_id 精确过滤
- `limit` (int): 返回条数，默认 100，最大 500
- `offset` (int): 偏移量，默认 0

**实现逻辑**：
- 读取日志文件（从末尾向前读取，支持大文件）
- 文本格式日志（app.log/error.log）：用正则解析 `时间 [级别] logger: message`
- JSON 格式日志（api.jsonl/perf.jsonl）：逐行 `json.loads`
- 按过滤条件筛选后返回结构化条目

**响应格式**：
```json
{
  "ok": true,
  "data": {
    "items": [
      {
        "timestamp": "2026-07-28 15:34:23",
        "level": "ERROR",
        "logger": "app.core.errors",
        "message": "Unhandled exception: ...",
        "request_id": "bffcd7f7608d",
        "traceback": "...",
        "file": "app.log",
        "line": 42
      }
    ],
    "total": 100,
    "file": "app.log"
  }
}
```

## 假设与决策

1. **日志文件读取方式**：直接读取文件系统中的日志文件（`logs/` 目录），不引入额外存储（如 Elasticsearch/Redis），保持架构简单
2. **大文件处理**：从文件末尾向前按块读取（每块 64KB），找到完整行后解析，最多读取 `limit` 条，避免全量加载
3. **contextvars 传播**：Python 3.11 的 `contextvars` 在 asyncio 中自动传播，无需额外处理
4. **日志级别优先级**：ERROR > WARNING > INFO > DEBUG，级别过滤时返回该级别及更高级别
5. **安全考虑**：日志 API 仅返回日志文件内容，`file` 参数做白名单校验（仅允许 `app.log`/`error.log`/`api.jsonl`/`perf.jsonl`），防止路径遍历
6. **移动端 Tab 数量**：添加日志后共 6 个 Tab，在窄屏上可能略挤，但 6 个 Tab 在大多数手机上仍可接受

## 验证步骤

1. **后端验证**：
   - `python3 -c "from app.main import app"` 确认无导入错误
   - 启动后端，访问 `GET /api/v1/logs/files` 确认返回日志文件列表
   - 访问 `GET /api/v1/logs?file=app.log&limit=10` 确认返回日志条目
   - 触发一个错误（如访问不存在的 API），确认日志中包含 request_id
   - 按 request_id 过滤确认能精准定位到对应请求的所有日志

2. **前端验证**：
   - `npx vite build` 确认构建通过
   - 访问 `/system/logs` 确认页面正常渲染
   - 测试级别过滤、关键词搜索、request_id 过滤功能
   - 测试日志展开查看 traceback
   - 确认暗色模式下样式正常

3. **端到端验证**：
   - 在前端触发一个操作（如创建策略失败）
   - 在日志页面通过 request_id 精准定位到该请求的所有相关日志
   - 确认能从日志中看到完整的错误堆栈
